Task: Stage 39 — Discovery-Led Implementation of Fintech Core (Escrow, Wallets & Commission)

ВНИМАНИЕ: Ты приступаешь к реализации финансового сердца платформы. Действуй по принципу «Сначала исследование, потом интеграция».

ЭТАП 1: Исследование (Discovery)
Beta Toggle: Найди в platform_settings ключ fintech_beta. Подтверди, как он ограничивает доступ сейчас. ЗАПРЕЩЕНО пересоздавать или ломать существующую логику рубильника.

Monetization: Проверь текущие заглушки цен в каталоге и бронировании.

OTP Service: Подтверди готовность методов lib/otp-service.ts и диспетчера уведомлений из Stage 38.
ОТЧЕТ: Выведи краткое резюме: «Структуру вижу, рубильник подтверждаю, готов к этапу 2».

ЭТАП 2: База данных и Атомарность
Схема Wallets: Создай таблицу wallets (userId, available_balance, frozen_balance, currency). Добавь индекс по userId.

Схема Transactions: Таблица с полями amount, platform_commission, type, status, reference_id.

Enum Types: 'hold', 'release', 'commission', 'payout', 'refund'.

Indices: Создай индексы по (userId, referenceId) и createdAt.

Pessimistic Locking: Все изменения баланса должны использовать транзакции БД с SELECT ... FOR UPDATE для конкретной строки кошелька.

ЭТАП 3: Логика Escrow и Математика
Математика комиссии: Реализуй расчет комиссии: amount * (percent / 100). Округляй до 2 знаков (копейки). Остаток при округлении — в пользу платформы.

Escrow Cycle (OTP-Protected):

Hold: При бронировании — перевод суммы в frozen_balance.

Start Verify: Ввод OTP владельцем при передаче — активация аренды.

End Verify: Ввод OTP владельцем при возврате — разморозка средств. Сумма (минус комиссия) уходит на available_balance владельца.

Notifications: После каждой финансовой операции (hold, release, payout) отправляй уведомление через гибридный диспетчер (TG/SMS) из Stage 38.

ЭТАП 4: UI и Управление
Dashboard: Секция «Кошелек» (балансы + история) видна только пользователям с активным fintech_beta.

Admin Panel: Раздел «Выплаты» (Payouts) для superadmin. Добавь в настройки переключатель payment_provider со значениями 'mock' и 'yookassa' (по умолчанию 'mock').

ЭТАП 5: Тестирование
Тест на race condition: два одновременных бронирования при балансе на одно.

Тест на безопасность: попытка вызова финтех-API без активного бета-рубильника (должен быть 403).

🛡️ Что это дает тебе как Архитектору:
Безопасность данных: Благодаря SELECT FOR UPDATE балансы никогда не «рассинхронятся», даже если тысячи людей нажмут «Забронировать» одновременно.

Юридическая чистота: Округление копеек и фиксация комиссии в каждой транзакции подготовят проект к реальной налоговой отчетности.

Гибкость: Переключатель 'mock' | 'yookassa' позволит тебе «включить настоящие деньги» одним кликом в админке, когда будешь готов.
